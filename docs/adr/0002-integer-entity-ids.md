# 0002. Integer IDs for new entities

- **Status:** Accepted
- **Date:** 2026-10-19

## Context

The template gives every entity a `Guid Id` (`src/Domain/Users/User.cs:5`, `src/Domain/Users/RefreshToken.cs:5`). The legacy database uses `INT IDENTITY` keys throughout (`legacy/Database/schema.sql:2, 13, 22`), and we want the new attendance model to use integer IDs as well.

## Decision

Every **new** entity uses an `int Id` key, generated by SQL Server as an `IDENTITY` column. The template's `User` and `RefreshToken` keep their `Guid` IDs, so any foreign key that points to a user stays a `Guid` (for example `OwnerId`, or `IUserContext.UserId`).

## Alternatives considered

- **Keep Guid for all entities.** Rejected because the user wants integer IDs, matching the legacy model.
- **Switch User and RefreshToken to int as well.** Rejected: the user chose to change new entities only and leave the template's user/auth code as generated.

## Consequences

- Handlers no longer set `Id = Guid.NewGuid()`. The database assigns the ID on `SaveChangesAsync`, and a create command returns it afterwards (`ICommand<int>`).
- Routes use `{id:int}`, error factories take `int`, and response DTOs expose `int Id`. The `add-entity` and `add-feature` skills are updated to match.
- The solution has two ID types: `int` for domain entities and `Guid` for users. Each foreign key keeps the type of the entity it points to.
- Integer IDs are sequential and easy to guess, so access must always be checked through authorization or ownership filters, never by relying on an ID being hard to guess.
- This decision does not imply that legacy IDs or data are migrated; data migration is out of scope.
